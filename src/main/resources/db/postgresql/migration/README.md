# Migrationen schreiben (PostgreSQL)

PostgreSQL 16 ist die einzige Datenbank: der eigene Server und alle Kunden
laufen darauf. Jede Aenderung am Datenbankschema ist **eine** Datei in diesem
Ordner:

    src/main/resources/db/postgresql/migration/V{N}__{beschreibung}.sql

- `N` = hoechste vorhandene Nummer + 1. Beschreibung klein, mit `_`.
- Eine Migration, die schon auf einem Server gelaufen ist, **nie mehr aendern**
  (Flyway merkt sich ihre Pruefsumme). Fehler korrigiert eine neue Migration.
- Neue Migration in `FlywayMigrationenTest.CHECKSUMMEN` eintragen - der Test
  schlaegt fehl und nennt die Zeile zum Einfuegen. So faellt spaeter jede
  versehentliche Aenderung auf (Flyway selbst prueft es nicht:
  `validate-on-migrate=false`).
- Der alte Ordner `db/migration/` (MySQL) ist weg. Liegt dort wieder etwas,
  scheitert der Build (`FlywayMigrationenTest`).
- Die Ordnernamen `db/postgresql/...` bleiben so, damit die Flyway-Historie der
  laufenden Installationen gueltig bleibt.

Alles bis V406 steckt schon in `db/postgresql/basis/V1__basis_schema.sql`
(Neuinstallation auf leerer Datenbank, siehe `FlywayStartSetupConfig`; neu
erzeugt mit `scripts/basis-schema/postgres_erzeugen.sh` - danach diese Zahl und
`FlywayMigrationenTest.LETZTE_MIGRATION_IN_DER_BASIS` anheben).

V407 und V408 verweisen in ihren Kommentaren auf die geloeschten MySQL-Dateien
(Kommentare gehoeren zur Pruefsumme, deshalb bleiben sie). Die Erklaerung steht
noch in der Git-Geschichte, z. B.
`git show 6f4efa2e:src/main/resources/db/migration/V407__email_postfaecher.sql`.

## Idempotent schreiben

Eine Migration muss einen zweiten Lauf ohne Fehler ueberstehen:

| Vorhaben                 | So schreiben                                              |
| ------------------------ | --------------------------------------------------------- |
| Tabelle anlegen          | `CREATE TABLE IF NOT EXISTS ...`                          |
| Spalte anlegen           | `ALTER TABLE t ADD COLUMN IF NOT EXISTS ...`              |
| Index anlegen            | `CREATE INDEX IF NOT EXISTS t__spalte ON t (spalte)`      |
| Spalte/Index entfernen   | `DROP ... IF EXISTS`                                      |
| Constraint neu anlegen   | erst `DROP CONSTRAINT IF EXISTS`, dann `ADD CONSTRAINT`   |
| Stammdaten einfuegen     | `INSERT ... ON CONFLICT DO NOTHING`                       |
| Bedingte Logik           | `DO $$ BEGIN IF NOT EXISTS (...) THEN ... END IF; END $$;` |
| Daten nachtragen         | `UPDATE ... WHERE spalte IS NULL` (trifft beim 2. Lauf nichts) |

## Spaltentypen

| Java / Zweck                       | PostgreSQL                                  |
| ---------------------------------- | ------------------------------------------- |
| `Long` id                          | `BIGINT GENERATED BY DEFAULT AS IDENTITY`   |
| `boolean`                          | `BOOLEAN`                                   |
| `LocalDateTime`                    | `TIMESTAMP(6)`                              |
| `LocalDate`                        | `DATE`                                      |
| `BigDecimal`                       | `NUMERIC(p, s)`                             |
| langer Text (`LONG32VARCHAR`)      | `TEXT`                                      |
| Bytes (`LONG32VARBINARY`)          | `BYTEA`                                     |
| Java-Enum (`EnumType.STRING`)      | `VARCHAR(n)` - **ohne** `CHECK (... IN (...))` |

Java-Enums bekommen keine Werteliste in der Datenbank: Ein neuer Enum-Wert soll
keine Migration brauchen (`FlywayMigrationenTest` prueft das). `n` mit etwas
Luft ueber dem laengsten Wert waehlen.

Die Typen muessen zur App passen - sie startet mit `ddl-auto=validate` und
bricht sonst ab.

## Worauf achten

- Namen ohne Anfuehrungszeichen schreiben (klein, mit `_`). Wo noetig `"name"`,
  nie Backticks.
- Indexnamen gelten in PostgreSQL im ganzen Schema, nicht je Tabelle - also
  eindeutig benennen, z. B. `tabelle__spalte`.
- Auf den Servern verbindet sich die App **ohne Superuser-Rechte** (Rolle
  `erp_user`, Eigentuemerin von Datenbank und Schema `public`, angelegt von
  `deployment/docker-server/postgres-init/01-app-rolle.sh`). Migrationen duerfen
  Tabellen, Indizes usw. anlegen und aendern, aber z. B. keine nicht
  vertrauenswuerdigen Erweiterungen (`CREATE EXTENSION`) installieren. Der
  Starttest und der CI-Job "Datenbank-Kompatibilitaet" pruefen genauso. Achtung:
  Im lokalen Dev-Container (`docker run ... -e POSTGRES_USER=erp_user`) ist
  `erp_user` Superuser - dort faellt so ein Fehler nicht auf.
- Keine Personendaten in Migrationen (Stammdaten nur mit Dummy-Werten).

## Pruefen

- `./mvnw test` - `FlywayMigrationenTest` prueft Dateinamen, Nummern,
  Enum-Regel und die festgeschriebenen Pruefsummen.
- Gegen ein echtes PostgreSQL (Wegwerf-Container `postgres:16`):
  `./mvnw test "-Dtest=DatenbankKompatibilitaet*Test" -Dkompat.db.url=jdbc:postgresql://localhost:5432/kompat -Dkompat.db.user=kompat -Dkompat.db.pass=kompat`
  - darunter `DatenbankKompatibilitaetMigrationenTest`: jede Migration laeuft ein
  zweites Mal auf dem fertigen Schema (idempotent?).
- Lokal starten: eine leere Datenbank bekommt Basis + alle Migrationen; eine
  bestehende nur die neuen.
- Der Starttest `deployment/docker-server/starttest.sh <image> [<kundenstand-image>]`
  spielt die Migration so ein wie das Nachtupdate beim Kunden.
