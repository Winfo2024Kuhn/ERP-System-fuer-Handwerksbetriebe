# ZUGFeRD & E-Invoicing – Elektronische Rechnungsstellung

> Stand: 12.10.2026 – Export mit echten Positionen, Steuersatz je Position, Zahlungsziel und Käuferanschrift; mit dem Mustang-Validator geprüft (PDF/A-3 und EN 16931 gültig).

## Übersicht

Dieses Dokument beschreibt die elektronische Rechnungsstellung (E-Invoicing) nach dem ZUGFeRD-Standard. Das System kann ZUGFeRD-Hybrid-PDFs **erstellen** (Ausgangsrechnungen aus dem Dokument-Editor) und **lesen** (Eingangsrechnungen von Lieferanten).

---

## 1. Ausgehende Rechnungen

### 1.1 Zweck

Erstellt ein ZUGFeRD-Hybrid-PDF: das sichtbare PDF aus dem Editor (PDF/A-3) mit eingebettetem XML (`factur-x.xml`) nach **EN 16931**.

### 1.2 Technologie

- **Mustang-Bibliothek**, Klasse `ZUGFeRDExporterFromA3`
- Profil: **EN 16931** (Kennung `urn:cen.eu:en16931:2017`, ZUGFeRD 2.3 / Factur-X), Syntax CII
- Version: Im `pom.xml` steht `library` 2.18.0. Der ebenfalls eingebundene `validator` 2.17.0 (`shaded`) bringt aber eigene `org.mustangproject`-Klassen mit und steht im Klassenpfad davor – tatsächlich läuft deshalb Mustang **2.17.0** (das XML trägt `generated by: mustangproject.org v2.17.0`).

### 1.3 Ablauf

```
Editor (document-editor)
    │  POST /api/dokument-generator/zugferd-pdf  (GeneratePdfRequest)
    ▼
DokumentGeneratorController.baueRechnungDto()
    │  → ein RechnungDto: Kopfdaten, Blöcke mit Zeilenbeträgen, Rabatt, Abrechnungsverlauf
    ├──────────────────────────────┐
    ▼                              ▼
RechnungPdfService           ZugferdRechnungMapper.ausRechnung()
  .generatePdfBytes()          → ZugferdDaten (Positionen, Abzüge, Anschrift, Fälligkeit)
    │                              │
    └──────────────┬───────────────┘
                   ▼
ZugferdErstellService.erzeuge(pdfPfad, zugferdDaten)
    │  → prüft die Firmendaten (Verkäufer), baut die Mustang-Rechnung, bettet das XML ein
    ▼
ZUGFeRD-Hybrid-PDF (PDF/A-3 + XML)
```

PDF und XML entstehen aus **demselben** `RechnungDto`. Der Mapper rechnet die Beträge genau wie der Summenblock im PDF (`RechnungPdfService#addSummenBlock`) – XML und Papier stimmen auf den Cent überein.

Vor dem Buchen fragt der Editor `GET /api/dokument-generator/zugferd-pruefung` ab (204 = Firmendaten reichen, sonst 422 mit Liste der fehlenden Angaben).

### 1.4 Methoden

```java
// ZugferdErstellService
Path erzeuge(String originalPdfPath, ZugferdDaten daten)   // Pfad zur temporären Hybrid-PDF
void pruefeVerkaeuferdaten()                               // wirft FirmenstammdatenUnvollstaendigException

// ZugferdRechnungMapper (@Component, in den Controller injiziert)
ZugferdDaten ausRechnung(RechnungDto rechnung)
```

### 1.5 Inhalt der E-Rechnung

| Bereich | Quelle | Umsetzung |
|---|---|---|
| Positionen (BG-25) | jede berechnete `SERVICE`-Position bis zum Abschluss-Block (`CLOSURE`) | eine Zeile je Position: Titel (BT-153), Langtext ohne HTML mit Absätzen als Zeilen (BT-154), Menge, Einzelpreis, Zeilenbetrag aus dem PDF. Alternativ-/Bedarfspositionen (`optional`) und alles hinter dem Abschluss-Block zählen wie im PDF nicht mit. |
| Einheit (BT-130) | Freitext der Position | `EinheitenCode`: Stk → H87, m/lfm → MTR, m² → MTK, m³ → MTQ, h/Std → HUR, kg → KGM, psch → LS … Unbekanntes → C62 („Einheit“). |
| Steuersatz | je Position (`ZugferdArtikelPosition.mwstSatz`) | Mustang bildet die Steueraufschlüsselung je Satz (BG-23). Editor und PDF kennen heute nur 19 % – deshalb liefert der Mapper überall 19 %. |
| Positionsrabatt | `rabattProzent` / Zeilenbetrag | Abzug auf Zeilenebene (BG-27) mit Grund „Rabatt 10 %“. Bemessen als `round2(Menge × Preis) − Zeilenbetrag`, damit genau der gedruckte Betrag entsteht. |
| Negativer Einzelpreis | z. B. „Material vom Kunden gestellt, −50 €“ | BR-27 verbietet negative Preise → positiver Preis, negative Menge; der Betrag bleibt gleich. |
| Pauschalrabatt | `globalRabattProzent` | Abzug auf Belegebene (BG-20), Betrag über `RabattRechner` wie die Rabattzeile im PDF. |
| Abschlagsrechnung | fester `betragNetto` | **eine** Zeile über den Abschlag („zu Auftragsbestätigung Nr. … vom …“); die Auftragspositionen im PDF zeigen nur den Auftrag. |
| Schlussrechnung | Abrechnungsverlauf mit Basisdokument | jede bereits gestellte Rechnung wird ein Abzug auf Belegebene („Bereits berechnet: Abschlagsrechnung Nr. …“) und ein Verweis auf die Vorrechnung (BG-3, Nummer und Datum) – wie im PDF nur mit Basisdokument. |
| Käufer (BG-7/BG-8) | Kundenname, Kundennummer, Rechnungsanschrift | Die Anschrift ist im Editor Freitext; der Mapper zerlegt sie: letzte Zeile mit PLZ + Ort, darüber die Straße, alle übrigen Zeilen werden Adresszusatz. Land aus Kennzeichen (`A-1010 Wien`, `E-28001 Madrid`) oder einer Länderzeile direkt unter dem Ort (`Schweiz`), sonst **DE** (BR-11). Eine erste Zeile gleich dem Kundennamen wird übersprungen. |
| Fälligkeit (BT-9) | `zahlungszielTage` | Rechnungsdatum + Zahlungsziel; ohne Angabe **8 Tage** wie der Editor (`DEFAULT_ZAHLUNGSZIEL_TAGE`). Zahlungsbedingung (BT-20) auf Deutsch: „Zahlbar bis 11.11.2026.“ Nur für Rechnung, Teil-, Abschlags- und Schlussrechnung und nur, wenn etwas zu zahlen ist. Angebot, Auftragsbestätigung, Gutschrift und Storno mit positivem Betrag bekommen stattdessen „Keine Zahlung fällig.“ (BR-CO-25 verlangt eine der beiden Angaben). |
| Dokumentart (BT-3) | Dokumenttyp im Editor | Gutschrift und Stornorechnung → 381 (Gutschrift), alles andere → 380 (Rechnung). |
| Leistungsdatum (BT-72) | `leistungsDatum` | `ActualDeliverySupplyChainEvent` |
| Verkäufer (BG-4) | Firmenstammdaten | Name, Anschrift, USt-IdNr. bzw. Steuernummer (BR-S-02, BR-CO-26), Kontakt und Bankverbindung, wenn hinterlegt. |

Ohne Positionen erzeugt `ZugferdErstellService` eine Sammelposition über `betragNetto` – fehlt der, wird er aus `betrag` und `mwstSatz` zurückgerechnet. Die alten Endpunkte `/api/anfragen|projekte/{id}/zugferd` nutzen immer diesen Weg: Positionen, Abzüge und Verweise aus der Client-Anfrage verwerfen sie, weil das hochgeladene PDF nur einen Betrag zeigt.

### 1.6 Prüfung und bekannte Grenzen

- **Validator:** `DokumentGeneratorControllerZugferdExportTest` erzeugt Rechnung, Schlussrechnung und Abschlagsrechnung über den echten Controller-Weg, prüft sie mit dem Mustang-Validator (PDF/A-3 und Schematron EN 16931 / ZUGFeRD 2.3.3) und gleicht den Zahlbetrag im XML mit dem Text des gedruckten PDFs ab. `ZugferdErstellServiceTest` prüft gemischte Sätze (7 % und 19 %), Positionsrabatt, negative Preise sowie Abzüge und Zuschläge.
- **Übrige Hinweise des Validators** stammen aus den XRechnung-/PEPPOL-Regeln (Leitweg-ID BT-10, XRechnung-Kennung BT-24, elektronische Adresse des Käufers). Sie gelten für Rechnungen an Behörden (B2G), nicht für ZUGFeRD im B2B-Verkehr.
- **Nur 19 %:** Editor, PDF-Summenblock und Mapper rechnen fest mit 19 %. 7 %, 0 % (Kleinunternehmer, §19 UStG) oder §13b (Steuerschuld des Leistungsempfängers) brauchen zuerst ein Feld im Editor und eine Aufschlüsselung im PDF; die E-Rechnung übernimmt den Satz je Position dann schon. Für 0 % bräuchte es zusätzlich die passende Steuerkategorie (E/AE statt S).
- **Abzüge zusammengefasst:** Mustang fasst Abzüge mit gleichem Steuersatz im XML zu einem zusammen und reiht die Gründe aneinander. Die Beträge stimmen.
- **Schlussrechnung als Nachlass:** Die Vorrechnungen stehen als Abzug auf Belegebene (BG-20) plus Verweis (BG-3) im XML. Das ist gültig und betragsgleich mit dem PDF; manche Empfängersysteme buchen einen BG-20-Abzug aber als Preisnachlass. Alternativen wären negative Positionen je Vorrechnung oder „bereits gezahlt“ (BT-113) – fachlich offen. Der PDF-Hinweis auf die in den Vorrechnungen enthaltene Umsatzsteuer (§14 Abs. 5 UStG) steht nicht im XML.
- **Leistungsdatum:** Der Editor schickt als Leistungsdatum das Rechnungsdatum; PDF und XML zeigen deshalb beide dieses Datum.
- **Dokumentart:** Abschlags- und Schlussrechnung laufen als 380; die Bau-Codes 875/877 wären genauer. Der Editor bietet das ZUGFeRD-Format für jeden Dokumenttyp an, auch für Angebot und Auftragsbestätigung – die bekommen dann eine gültige E-Rechnung (380) mit „Keine Zahlung fällig.“, obwohl sie keine Rechnungen sind.
- **Mehrere Vorrechnungs-Verweise (BG-3):** Der Mustang-Validator (ZUGFeRD 2.3.3) akzeptiert sie. Ältere CII-Fassungen (ZUGFeRD 2.1/2.2) erlauben nur einen – mit dem KoSIT-Validator noch nicht gegengeprüft.
- **XRechnung (reines XML für Behörden)** wird nicht erzeugt.

## 2. Eingehende Rechnungen (`ZugferdExtractorService`)

### 2.1 Zweck

Extrahiert strukturierte Rechnungsdaten aus ZUGFeRD-PDFs (eingebettetes XML).

### 2.2 Methode

```java
ZugferdDaten extract(String pdfPath, String originalFilename)
```

### 2.3 Extrahierte Felder

| Feld | ZUGFeRD-Mapping | Beschreibung |
|---|---|---|
| `rechnungsnummer` | Invoice Number | Rechnungsnummer |
| `rechnungsdatum` | Issue Date | Rechnungsdatum |
| `faelligkeitsdatum` | Due Date | Fälligkeitsdatum (fehlt bei bereits bezahlten Rechnungen) |
| `betrag` | Amount (Mustang `getAmount()`) | Bruttobetrag |
| `betragNetto` | Tax Basis Total Amount (BT-109) | Nettobetrag – aus der Rechnung gelesen; nur ohne BT-109 aus Brutto und Satz zurückgerechnet |
| `mwstSatz` | Rate Applicable Percent | Satz als **Anteil** (0.19), nur wenn die Rechnung genau einen Satz ausweist; bei gemischten Sätzen `null` |
| `kundenName` | Buyer Name | Kundenname |
| `kundennummer` | Buyer ID | Kundennummer |
| `bestellnummer` | Buyer Order Reference | Eigene Bestellnummer |
| `referenzNummer` | Seller Order / Contract Reference | Referenz des Lieferanten (AB-Nummer, Vertrag) |
| `skontoProzent` | Cash Discount Percent | Skonto-Prozentsatz |
| `skontoTage` | Cash Discount Days | Skontotage |
| `nettoTage` | aus Fälligkeit − Rechnungsdatum | Netto-Zahlungsziel |
| `bereitsGezahlt` | Total Prepaid Amount ≥ Brutto | bereits bezahlt (Amazon, Vorauskasse) |
| `geschaeftsdokumentart` / `typeCode` | Document Type (UNTDID 1001) | Dokumenttyp, `UntdidCodeliste` |
| `artikelPositionen` | Line Items | Einzelne Rechnungspositionen |

### 2.4 Artikelpositionen (`ZugferdArtikelPosition`)

| Feld | Beschreibung |
|---|---|
| `externeArtikelnummer` | Artikelnummer des Lieferanten |
| `bezeichnung` | Artikelbezeichnung |
| `menge` | Menge |
| `mengeneinheit` | Einheit (Stück, kg, m etc.) |
| `einzelpreis` | Preis pro Einheit |
| `preiseinheit` | Preiseinheit |
| `gesamtpreisNetto` | Zeilenbetrag netto |

Nur beim Erstellen genutzt: `beschreibung` (Langtext), `mwstSatz` (Satz der Position), `rabattProzent` (Text des Positionsrabatts).

## 4. Fallback-Kette bei Eingangsrechnungen

### 4.1 Priorisierte Extraktionsmethoden

```
[1] ZUGFeRD-XML in PDF vorhanden?
     │
     ├── JA → ZugferdExtractorService.extract()
     │         datenquelle = "ZUGFERD"
     │         verifiziert = true
     │
     └── NEIN ↓

[2] XML-Datei (XRechnung, ZUGFeRD-XML)?
     │
     ├── JA → XML-Parsing (GeminiDokumentAnalyseService)
     │         datenquelle = "XML"
     │         verifiziert = true
     │
     └── NEIN ↓

[3] Dateiname-Parsing
     │
     └── Regex auf Dateinamen für Dokumentnummer/Datum
         ↓

[4] KI-Analyse (Gemini AI)
     │
     └── GeminiDokumentAnalyseService
           datenquelle = "AI"
           verifiziert = false
           aiConfidence = 0.0–1.0
           manuellePruefungErforderlich = true/false
```

`verifiziert` heißt „strukturiert gelesen, nicht geschätzt“ (siehe `LieferantGeschaeftsdokument`). Gelesen wird das Feld derzeit nirgends.

### 4.2 Vergleich der Methoden

| Methode | Zuverlässigkeit | Auto-Verifiziert | Geschwindigkeit |
|---|---|---|---|
| ZUGFeRD | ★★★★★ | ✅ Ja | ⚡ Schnell |
| XML | ★★★★☆ | ✅ Ja | ⚡ Schnell |
| Dateiname-Parsing | ★★☆☆☆ | ❌ Nein | ⚡ Schnell |
| Gemini AI (OCR) | ★★★☆☆ | ❌ Nein | 🐢 Langsam (API-Call) |

## 5. Feldmapping

### 5.1 Ausgehend (Editor → ZUGFeRD)

| Editor / `RechnungDto` | ZUGFeRD-Feld |
|---|---|
| Dokumentnummer | Invoice Number (BT-1) |
| Rechnungsdatum | Issue Date (BT-2) |
| Leistungsdatum | Actual Delivery Date (BT-72) |
| Rechnungsdatum + Zahlungsziel | Due Date (BT-9), Payment Terms (BT-20) |
| Kundenname, Kundennummer | Buyer Name (BT-44), Buyer ID (BT-46) |
| Rechnungsanschrift | Buyer Address (BT-50 … BT-55) |
| Position: Titel, Langtext, Menge, Einheit, Einzelpreis | Item Name (BT-153), Description (BT-154), Quantity (BT-129), Unit (BT-130), Net Price (BT-146) |
| Position: Rabatt | Line Allowance (BG-27) |
| Pauschalrabatt, bereits gestellte Rechnungen | Document Allowance (BG-20) |
| Firmenstammdaten | Seller (BG-4), Payment Instructions (BG-16) |

Netto, Steuer und Brutto (BT-106 … BT-115) rechnet Mustang aus den Zeilen und Abzügen.

| Tax Basis Total Amount | `betragNetto` |
| Tax Percent (nur bei einem Satz) | `mwstSatz` |
| Buyer Order Reference | `bestellnummer` |
| Payment Reference | `referenzNummer` |
| Cash Discount Percent | `skontoProzent` |
| Cash Discount Days | `skontoTage` |
| Net Payment Days | `nettoTage` |

## 6. Gesetzliche Anforderungen

### 6.1 E-Rechnungspflicht

| Zeitraum | Pflicht | Bereich |
|---|---|---|
| Ab 01.01.2025 | E-Rechnungspflicht | **B2G** (Business-to-Government) |
| Ab 01.01.2025 | Empfangspflicht | **B2B** (alle Unternehmen müssen E-Rechnungen empfangen können) |
| Ab 01.01.2027 | Versandpflicht | **B2B** (Unternehmen > 800.000 € Umsatz) |
| Ab 01.01.2028 | Versandpflicht | **B2B** (alle Unternehmen) |

### 6.2 Unterstützte Formate

| Format | Beschreibung | Status |
|---|---|---|
| **ZUGFeRD 2.x (EN 16931)** | Hybrid-PDF (PDF/A-3 + XML) | ✅ Erstellen und Lesen |
| **Factur-X** | Französisch-deutsches Pendant zu ZUGFeRD | ✅ Lesen (gleiche Basis) |
| **XRechnung** | Reines XML-Format (B2G) | ⚠️ Nur Lesen |

### 6.3 Anforderungen an E-Rechnungen

- **Strukturierte Daten**: Maschinenlesbares XML mit Pflichtfeldern
- **Integrität**: PDF/A-3 Standard für Langzeitarchivierung
- **Vollständigkeit**: Rechnungsnummer, Datum, Leistungsdatum, Positionen, Beträge, MwSt, Empfänger mit Anschrift
- **Normenkonformität**: EN 16931 (europäische Norm für elektronische Rechnungen)

## 7. Datenmodell (`ZugferdDaten`)

### 7.1 Hauptfelder

| Feld | Typ | Beschreibung |
|---|---|---|
| `geschaeftsdokumentart` | `String` | Dokumenttyp (Rechnung, Gutschrift etc.) |
| `typeCode` | `String` | roher UNTDID-1001-Code (nur beim Lesen) |
| `rechnungsnummer` | `String` | Rechnungsnummer |
| `rechnungsdatum` | `LocalDate` | Rechnungsdatum |
| `leistungsdatum` | `LocalDate` | Leistungsdatum (nur beim Erstellen) |
| `zahlungsbedingung` | `String` | Zahlungsbedingung ohne Fälligkeit, etwa „Keine Zahlung fällig.“ (nur beim Erstellen) |
| `faelligkeitsdatum` | `LocalDate` | Fälligkeitsdatum |
| `betrag` | `BigDecimal` | Bruttobetrag |
| `betragNetto` | `BigDecimal` | Nettobetrag |
| `mwstSatz` | `BigDecimal` | Steuersatz; Prozent (19) oder Anteil (0.19), `ZugferdErstellService` versteht beides |
| `kundenName` | `String` | Kundenname |
| `kundennummer` | `String` | Kundennummer |
| `kundenStrasse`, `kundenAdresszusatz`, `kundenPlz`, `kundenOrt`, `kundenLand` | `String` | Käuferanschrift; `kundenLand` als ISO-Code, leer = DE |
| `email` | `String` | elektronische Adresse des Käufers (optional) |
| `bestellnummer` | `String` | Eigene Bestellnummer |
| `referenzNummer` | `String` | Referenz des Lieferanten |
| `skontoProzent` | `BigDecimal` | Skonto-Prozentsatz |
| `skontoTage` | `Integer` | Skontotage |
| `nettoTage` | `Integer` | Netto-Zahlungsziel |
| `bereitsGezahlt` | `Boolean` | laut XML schon bezahlt |
| `artikelPositionen` | `List<ZugferdArtikelPosition>` | Einzelpositionen |
| `abzuege` | `List<ZugferdAbzug>` | Abzüge auf die ganze Rechnung (nur beim Erstellen) |
| `vorrechnungen` | `List<ZugferdBelegverweis>` | Verweise auf vorausgegangene Rechnungen, BG-3 (nur beim Erstellen) |

### 7.2 `ZugferdAbzug`

`record ZugferdAbzug(String grund, BigDecimal betragNetto, BigDecimal mwstSatz)` – Abzug auf Belegebene (BG-20), bei negativem Betrag Zuschlag (BG-21). Ohne Grund steht „Nachlass“ bzw. „Zuschlag“, ohne Satz gilt der Satz der Rechnung.

`record ZugferdBelegverweis(String nummer, LocalDate datum)` – Verweis auf eine vorausgegangene Rechnung (BG-3: BT-25, BT-26).
