# ZUGFeRD & E-Invoicing – Elektronische Rechnungsstellung

> Stand: 12.10.2026 – Export mit echten Positionen, Steuersatz je Position, Zahlungsziel und Käuferanschrift; mit dem Mustang-Validator geprüft (PDF/A-3 und EN 16931 gültig).

## Übersicht

Dieses Dokument beschreibt die Implementierung der elektronischen Rechnungsstellung (E-Invoicing) im Kalkulationsprogramm nach dem ZUGFeRD-Standard. Das System unterstützt sowohl das **Erstellen** von ZUGFeRD-Hybrid-PDFs (PDF mit eingebettetem XML) als auch das **Lesen** von ZUGFeRD-PDFs und XML-E-Rechnungen (XRechnung, ZUGFeRD-XML).

**Kurz für die Praxis:**
- E-Rechnung verschicken: im Dokument-Editor auf **„E-Mail“** oder **„PDF“** klicken und **„ZUGFeRD PDF“** wählen („PDF mit maschinenlesbaren Rechnungsdaten (EN 16931)“).
- Vorher müssen die Firmendaten vollständig sein (Vorlagen & Stammdaten → Administration → **Firma** → Reiter „Firmendaten“): Firmenname, Straße, Postleitzahl, Ort und Umsatzsteuer-ID oder Steuernummer. Fehlt etwas, meldet das Programm z. B. „Für die E-Rechnung fehlen Angaben zu Ihrem Betrieb: Postleitzahl. Bitte unter „Firma“ ergänzen.“ – und die Rechnung wird **nicht** gebucht.
- Die E-Rechnung enthält dieselben Positionen und Beträge wie das gedruckte PDF, die Kundenanschrift aus dem Adressfeld und das Zahlungsziel des Dokuments.
- E-Rechnungen von Lieferanten (ZUGFeRD-PDF oder XML) werden beim Eingang automatisch ausgelesen – ganz ohne KI.

## 1. Ausgehende Rechnungen (`ZugferdErstellService`)

### 1.1 Zweck

Erstellt ZUGFeRD-konforme Hybrid-PDFs, die sowohl menschenlesbares PDF als auch maschinenlesbares XML enthalten.

### 1.2 Technologie

- **Mustang-Bibliothek** (`org.mustangproject:library` 2.18.0), Klasse `ZUGFeRDExporterFromA3`
- Profil: Das Profil wird im Code nicht ausdrücklich gesetzt; es gilt die Vorgabe der Mustang-Bibliothek: **EN 16931 (COMFORT)**, Kennung `urn:cen.eu:en16931:2017`, ZUGFeRD 2 / Factur-X, Syntax CII
- Ergebnis: PDF/A-3 mit eingebettetem XML
- Version zur Laufzeit: Der ebenfalls eingebundene `org.mustangproject:validator` 2.17.0 (`shaded`) bringt eigene `org.mustangproject`-Klassen mit und steht im Klassenpfad davor – tatsächlich läuft deshalb Mustang **2.17.0** (das XML trägt `generated by: mustangproject.org v2.17.0`).

### 1.3 Ablauf

```
Dokument-Editor: "E-Mail" oder "PDF" → Format "ZUGFeRD PDF"
    │
    ▼
GET /api/dokument-generator/zugferd-pruefung
    │  → Firmendaten vollständig? (204 = ok, 422 = Meldung mit fehlenden Angaben)
    │
    ▼
Rechnung buchen & sperren (nur Rechnungstypen)
    │
    ▼
POST /api/dokument-generator/zugferd-pdf
    │  1. DokumentGeneratorController.baueRechnungDto(): ein RechnungDto
    │     (Kopfdaten, Blöcke mit Zeilenbeträgen, Rabatt, Abrechnungsverlauf)
    │  2. RechnungPdfService.generatePdfBytes(rechnungDto) → sichtbares PDF (OpenPDF)
    │  3. ZugferdRechnungMapper.ausRechnung(rechnungDto) → ZugferdDaten
    │  4. ZugferdErstellService.erzeuge(pdfPfad, zugferdDaten)
    │     → bettet ZUGFeRD-XML ein, erzeugt temporäre Datei
    │
    ▼
ZUGFeRD-Hybrid-PDF (PDF/A-3 + eingebettetes XML) als Download bzw. E-Mail-Anhang
```

PDF und XML entstehen aus **demselben** `RechnungDto`. Der Mapper rechnet die Beträge genau wie der Summenblock im PDF (`RechnungPdfService#addSummenBlock`) – XML und Papier stimmen auf den Cent überein.

### 1.4 Methoden

```java
// ZugferdErstellService
Path erzeuge(String originalPdfPath, ZugferdDaten daten)   // Pfad zur temporären Hybrid-PDF
void pruefeVerkaeuferdaten()                               // wirft FirmenstammdatenUnvollstaendigException

// ZugferdRechnungMapper (@Component, in den Controller injiziert)
ZugferdDaten ausRechnung(RechnungDto rechnung)
```

`pruefeVerkaeuferdaten()` prüft vorab nur die Firmendaten, ohne etwas zu erzeugen.

### 1.5 Inhalt des eingebetteten XML

| Bereich | Quelle | Umsetzung |
|---|---|---|
| Rechnungsnummer, -datum | Dokumentnummer und -datum | fehlt das Datum: heute |
| Dokumentart (BT-3) | Dokumenttyp im Editor | Gutschrift und Stornorechnung → 381 (Gutschrift), alles andere → 380 (Rechnung) |
| Positionen (BG-25) | jede berechnete `SERVICE`-Position bis zum Abschluss-Block (`CLOSURE`) | eine Zeile je Position: Titel (BT-153), Langtext ohne HTML mit Absätzen als Zeilen (BT-154), Menge, Einzelpreis, Zeilenbetrag aus dem PDF. Alternativ-/Bedarfspositionen (`optional`) und alles hinter dem Abschluss-Block zählen wie im PDF nicht mit. |
| Einheit (BT-130) | Freitext der Position | `EinheitenCode`: Stk → H87, m/lfm → MTR, m² → MTK, m³ → MTQ, h/Std → HUR, kg → KGM, psch → LS … Unbekanntes → C62 („Einheit“). |
| Steuersatz | je Position (`ZugferdArtikelPosition.mwstSatz`) | Mustang bildet die Steueraufschlüsselung je Satz (BG-23). Editor und PDF kennen heute nur 19 % – deshalb liefert der Mapper überall 19 %. |
| Positionsrabatt | `rabattProzent` / Zeilenbetrag | Abzug auf Zeilenebene (BG-27) mit Grund „Rabatt 10 %“. Bemessen als `round2(Menge × Preis) − Zeilenbetrag`, damit genau der gedruckte Betrag entsteht. |
| Negativer Einzelpreis | z. B. „Material vom Kunden gestellt, −50 €“ | BR-27 verbietet negative Preise → positiver Preis, negative Menge; der Betrag bleibt gleich. |
| Pauschalrabatt | `globalRabattProzent` | Abzug auf Belegebene (BG-20), Betrag über `RabattRechner` wie die Rabattzeile im PDF. |
| Abschlagsrechnung | fester `betragNetto` | **eine** Zeile über den Abschlag („zu Auftragsbestätigung Nr. … vom …“); die Auftragspositionen im PDF zeigen nur den Auftrag. |
| Schlussrechnung | Abrechnungsverlauf mit Basisdokument | jede bereits gestellte Rechnung wird ein Abzug auf Belegebene („Bereits berechnet: Abschlagsrechnung Nr. …“) und ein Verweis auf die Vorrechnung (BG-3, Nummer und Datum) – wie im PDF nur mit Basisdokument. |
| Käufer (BG-7/BG-8) | Kundenname, Kundennummer, Rechnungsanschrift | Die Anschrift ist im Editor Freitext; der Mapper zerlegt sie: letzte Zeile mit PLZ + Ort, darüber die Straße, alle übrigen Zeilen werden Adresszusatz. Land aus Kennzeichen (`A-1010 Wien`, `E-28001 Madrid`) oder einer Länderzeile direkt unter dem Ort (`Schweiz`), sonst **DE** (BR-11). Eine erste Zeile gleich dem Kundennamen wird übersprungen; fehlt der Name: „Kunde“. |
| Fälligkeit (BT-9) | `zahlungszielTage` | Rechnungsdatum + Zahlungsziel; ohne Angabe **8 Tage** wie der Editor (`DEFAULT_ZAHLUNGSZIEL_TAGE`). Zahlungsbedingung (BT-20) auf Deutsch: „Zahlbar bis 11.11.2026.“ Nur für Rechnung, Teil-, Abschlags- und Schlussrechnung und nur, wenn etwas zu zahlen ist. Angebot, Auftragsbestätigung, Gutschrift und Storno mit positivem Betrag bekommen stattdessen „Keine Zahlung fällig.“ (BR-CO-25 verlangt eine der beiden Angaben). |
| Leistungsdatum (BT-72) | `leistungsDatum` | `ActualDeliverySupplyChainEvent` |
| Verkäufer (BG-4) | Firmendaten | Name, Straße, PLZ, Ort, Land `DE`, USt-IdNr. und/oder Steuernummer (ohne USt-IdNr. dient die Steuernummer zugleich als Kennung, BR-CO-26), Kontakt (Geschäftsführer bzw. Firmenname, Telefon, E-Mail), Bankverbindung (IBAN, BIC), falls hinterlegt |

Netto, Steuer und Brutto (BT-106 … BT-115) rechnet Mustang aus den Zeilen und Abzügen.

Ohne Positionen erzeugt `ZugferdErstellService` eine Sammelposition über `betragNetto` – fehlt der, wird er aus `betrag` und `mwstSatz` zurückgerechnet. Die alten Endpunkte `/api/anfragen|projekte/{id}/zugferd` nutzen immer diesen Weg: Positionen, Abzüge und Verweise aus der Client-Anfrage verwerfen sie, weil das hochgeladene PDF nur einen Betrag zeigt.

**Prüfung der Firmendaten (`baueVerkaeufer`)** – fehlt etwas, wird mit `FirmenstammdatenUnvollstaendigException` (HTTP 422) abgebrochen:
- Firmenname, Straße, Postleitzahl, Ort
- Umsatzsteuer-ID **oder** Steuernummer
- Eine angegebene USt-IdNr. muss mit dem Ländercode beginnen (Format `DE123456789`)

### 1.6 Prüfung

- **Validator:** `DokumentGeneratorControllerZugferdExportTest` erzeugt Rechnung, Schlussrechnung, Abschlagsrechnung, Storno und Angebot über den echten Controller-Weg, prüft sie mit dem Mustang-Validator (PDF/A-3 und Schematron EN 16931 / ZUGFeRD 2.3.3) und gleicht den Zahlbetrag im XML mit dem Text des gedruckten PDFs ab. `ZugferdErstellServiceTest` prüft gemischte Sätze (7 % und 19 %), Positionsrabatt, negative Preise, Abzüge und Zuschläge sowie Vorrechnungs-Verweise.
- **Übrige Hinweise des Validators** stammen aus den XRechnung-/PEPPOL-Regeln (Leitweg-ID BT-10, XRechnung-Kennung BT-24, elektronische Adresse des Käufers). Sie gelten für Rechnungen an Behörden (B2G), nicht für ZUGFeRD im B2B-Verkehr.
- Bekannte Grenzen: siehe Abschnitt 6.4.

## 2. Eingehende Rechnungen (`ZugferdExtractorService`)

### 2.1 Zweck

Extrahiert strukturierte Rechnungsdaten aus ZUGFeRD-PDFs (eingebettetes XML).

### 2.2 Methode

```java
ZugferdDaten extract(String pdfPath, String originalFilename)
```

Ist das PDF keine ZUGFeRD-Datei, wird ein fast leeres `ZugferdDaten` zurückgegeben (nur der aus dem Dateinamen geratene Dokumenttyp) – es gibt keine Exception.

### 2.3 Extrahierte Felder

| Feld | ZUGFeRD-Quelle | Beschreibung |
|---|---|---|
| `rechnungsnummer` | Invoice ID | Rechnungsnummer |
| `rechnungsdatum` | Issue Date | Rechnungsdatum |
| `faelligkeitsdatum` | Due Date | Fälligkeitsdatum (falls vorhanden) |
| `betrag` | Grand Total Amount | Bruttobetrag |
| `betragNetto` | Tax Basis Total Amount (BT-109) | Nettobetrag – aus der Rechnung gelesen; nur ohne BT-109 aus Brutto und Satz zurückgerechnet |
| `mwstSatz` | Rate Applicable Percent | Satz als **Anteil** (0.19), nur wenn die Rechnung genau einen Satz ausweist; bei gemischten Sätzen `null` |
| `bereitsGezahlt` | Total Prepaid Amount | `true`, wenn der bereits gezahlte Betrag den Bruttobetrag deckt (z. B. Vorauskasse) |
| `kundenName` | Buyer Name | Name des Rechnungsempfängers (Umlaute werden repariert) |
| `kundennummer` | Buyer ID | Kundennummer |
| `bestellnummer` | Buyer Order Reference / Buyer Reference | Unsere Bestellnummer beim Lieferanten |
| `referenzNummer` | Seller Order Reference, Contract Reference, Seller Reference, Project Reference | Referenz des Lieferanten (AB-Nummer, Vertrag, Projekt) |
| `skontoProzent` | Payment Discount Terms – Percent | Skonto-Prozentsatz |
| `skontoTage` | Payment Discount Terms – Basis Period | Skontotage |
| `typeCode` | TypeCode (UNTDID 1001) | Roher Dokumenttyp-Code |
| `geschaeftsdokumentart` | aus TypeCode, sonst Dateiname | z. B. Rechnung, Gutschrift, Auftragsbestätigung, Lieferschein, Angebot |
| `artikelPositionen` | Line Items (CII und UBL) | Einzelne Rechnungspositionen |
| `nettoTage` | **berechnet** | Tage zwischen Rechnungs- und Fälligkeitsdatum |

### 2.4 Artikelpositionen (`ZugferdArtikelPosition`)

Jede Rechnungsposition enthält:

| Feld | Beschreibung |
|---|---|
| `externeArtikelnummer` | Artikelnummer des Lieferanten (bzw. des Käufers) |
| `bezeichnung` | Artikelbezeichnung |
| `menge` | Menge (auch negativ, z. B. Rücknahme) |
| `mengeneinheit` | Einheit (Stück, kg, m etc.) |
| `einzelpreis` | Preis pro Einheit |
| `preiseinheit` | Preiseinheit (z. B. t, 100 kg) |
| `gesamtpreisNetto` | Positionsbetrag netto |

Nur beim Erstellen genutzt: `beschreibung` (Langtext), `mwstSatz` (Satz der Position), `rabattProzent` (Text des Positionsrabatts).

Die Positionen fließen in die Preisübernahme für den Artikelstamm – aber nur, wenn der TypeCode der Datei das Dokument wirklich als Rechnung ausweist.

## 4. Auslese-Kette bei Eingangsrechnungen

### 4.1 Priorisierte Extraktionsmethoden (`DokumentAnalyseService`)

```
[1] PDF mit eingebettetem ZUGFeRD-XML?
     │
     ├── JA → ZugferdExtractorService.extract()
     │         datenquelle = "ZUGFERD"
     │         verifiziert = true, aiConfidence = 1.0
     │         (Höchste Zuverlässigkeit)
     │
     └── NEIN ↓

[2] XML-Datei (XRechnung oder ZUGFeRD-XML)?
     │
     ├── JA → XML-Parsing
     │         datenquelle = "XML"
     │         verifiziert = true, aiConfidence = 1.0
     │
     └── NEIN ↓

[3] KI-Analyse (Google Gemini) – für PDF, JPG, PNG
     │
     └── verifiziert = false
         aiConfidence = 0.0–1.0 (von der KI geliefert)
         manuellePruefungErforderlich = true, wenn Pflichtfelder fehlen
         (vorher zweiter Versuch mit dem Pro-Modell, falls ein eigenes konfiguriert ist)
```

Der Dateiname wird nur genutzt, um den Dokumenttyp zu erraten – er ist keine eigene Auslese-Stufe. Die KI braucht einen hinterlegten Gemini-Schlüssel (Einstellungen → Reiter „KI-Funktionen“).

`verifiziert` heißt „strukturiert gelesen, nicht geschätzt“ (siehe `LieferantGeschaeftsdokument`). Gelesen wird das Feld derzeit nirgends.

### 4.2 Vergleich der Methoden

| Methode | Zuverlässigkeit | Auto-Verifiziert | Geschwindigkeit |
|---|---|---|---|
| ZUGFeRD | ★★★★★ | ✅ Ja | ⚡ Schnell |
| XML | ★★★★☆ | ✅ Ja | ⚡ Schnell |
| KI (Gemini) | ★★★☆☆ | ❌ Nein | 🐢 Langsam (API-Call) |

### 4.3 Wo E-Rechnungen ankommen

- **E-Mail-Anhänge** von Lieferanten (PDF oder XML) werden automatisch als Lieferanten-Dokument abgelegt und ausgelesen
- **Lieferanten** → Dokumente hochladen
- **Rechnungen** (Rechnungsübersicht) → „Rechnung/Gutschrift manuell importieren“ (PDF, XML, JPG, PNG; max. 25 MB)

## 6. Gesetzliche Anforderungen

### 6.1 E-Rechnungspflicht

| Zeitraum | Pflicht | Bereich |
|---|---|---|
| Seit 27.11.2020 | E-Rechnung an Bundesbehörden (Länder mit eigenen Fristen) | **B2G** (Business-to-Government) |
| Ab 01.01.2025 | Empfangspflicht | **B2B** (alle Unternehmen müssen E-Rechnungen empfangen können) |
| Ab 01.01.2027 | Versandpflicht | **B2B** (Unternehmen mit mehr als 800.000 € Vorjahresumsatz) |
| Ab 01.01.2028 | Versandpflicht | **B2B** (alle Unternehmen) |

Rechnungen an Privatkunden (B2C) sind nicht betroffen. Fristen und Ausnahmen (z. B. Kleinbetragsrechnungen) im Zweifel mit dem Steuerberater klären.

### 6.2 Unterstützte Formate

| Format | Beschreibung | Status |
|---|---|---|
| **ZUGFeRD 2 (Profil EN 16931)** | Hybrid-PDF (PDF/A-3 + XML) | ✅ Erstellen und Lesen |
| **Factur-X** | Französisch-deutsches Pendant zu ZUGFeRD | ✅ Lesen (gleiche Basis) |
| **XRechnung** | Reines XML-Format (kein PDF) | ⚠️ Nur Lesen (CII und UBL); Erstellen nicht möglich |

### 6.3 Anforderungen an E-Rechnungen

- **Strukturierte Daten**: Maschinenlesbares XML mit Pflichtfeldern
- **Integrität**: PDF/A-3 Standard für Langzeitarchivierung
- **Vollständigkeit**: Rechnungsnummer, Datum, Leistungsdatum, Positionen, Beträge, MwSt, Empfänger mit Anschrift
- **Normenkonformität**: EN 16931 (europäische Norm für elektronische Rechnungen)

### 6.4 Bekannte Einschränkungen der erzeugten E-Rechnung

- **Nur 19 %:** Editor, PDF-Summenblock und Mapper rechnen fest mit 19 %. 7 %, 0 % (Kleinunternehmer, §19 UStG) oder §13b (Steuerschuld des Leistungsempfängers) brauchen zuerst ein Feld im Editor und eine Aufschlüsselung im PDF; die E-Rechnung übernimmt den Satz je Position dann schon. Für 0 % bräuchte es zusätzlich die passende Steuerkategorie (E/AE statt S).
- **Abzüge zusammengefasst:** Mustang fasst Abzüge mit gleichem Steuersatz im XML zu einem zusammen und reiht die Gründe aneinander. Die Beträge stimmen.
- **Schlussrechnung als Nachlass:** Die Vorrechnungen stehen als Abzug auf Belegebene (BG-20) plus Verweis (BG-3) im XML. Das ist gültig und betragsgleich mit dem PDF; manche Empfängersysteme buchen einen BG-20-Abzug aber als Preisnachlass. Alternativen wären negative Positionen je Vorrechnung oder „bereits gezahlt“ (BT-113) – fachlich offen. Der PDF-Hinweis auf die in den Vorrechnungen enthaltene Umsatzsteuer (§14 Abs. 5 UStG) steht nicht im XML.
- **Mehrere Vorrechnungs-Verweise (BG-3):** Der Mustang-Validator (ZUGFeRD 2.3.3) akzeptiert sie. Ältere CII-Fassungen (ZUGFeRD 2.1/2.2) erlauben nur einen – mit dem KoSIT-Validator noch nicht gegengeprüft.
- **Dokumentart:** Abschlags- und Schlussrechnung laufen als 380; die Bau-Codes 875/877 wären genauer. Der Editor bietet das ZUGFeRD-Format für jeden Dokumenttyp an, auch für Angebot und Auftragsbestätigung – die bekommen dann eine gültige E-Rechnung (380) mit „Keine Zahlung fällig.“, obwohl sie keine Rechnungen sind.
- **Leistungsdatum:** Der Editor schickt als Leistungsdatum das Rechnungsdatum; PDF und XML zeigen deshalb beide dieses Datum.
- **XRechnung (reines XML für Behörden)** wird nicht erzeugt.

## 7. Datenmodell (`ZugferdDaten`)

### 7.1 Hauptfelder

| Feld | Typ | Beschreibung |
|---|---|---|

| `skontoProzent` | `BigDecimal` | Skonto-Prozentsatz |

| `nettoTage` | `Integer` | Netto-Zahlungsziel |
| `referenzDokumentId`, `mahnstufe` | `Long`, `String` | Für hochgeladene Mahnungen |
| `artikelPositionen` | `List<ZugferdArtikelPosition>` | Einzelpositionen |
| `abzuege` | `List<ZugferdAbzug>` | Abzüge auf die ganze Rechnung (nur beim Erstellen) |
| `vorrechnungen` | `List<ZugferdBelegverweis>` | Verweise auf vorausgegangene Rechnungen, BG-3 (nur beim Erstellen) |

### 7.2 Hilfstypen

`record ZugferdAbzug(String grund, BigDecimal betragNetto, BigDecimal mwstSatz)` – Abzug auf Belegebene (BG-20), bei negativem Betrag Zuschlag (BG-21). Ohne Grund steht „Nachlass“ bzw. „Zuschlag“, ohne Satz gilt der Satz der Rechnung.

`record ZugferdBelegverweis(String nummer, LocalDate datum)` – Verweis auf eine vorausgegangene Rechnung (BG-3: BT-25, BT-26).

## 8. API-Referenz

| Methode | Pfad | Beschreibung |
|---|---|---|
| `GET` | `/api/dokument-generator/zugferd-pruefung` | Firmendaten für E-Rechnung prüfen (204 oder 422) |
