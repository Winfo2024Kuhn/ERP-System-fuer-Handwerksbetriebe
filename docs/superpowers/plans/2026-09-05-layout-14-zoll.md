## Global Constraints

**Umfang**

- Nur `react-pc-frontend/` wird angefasst. **Kein Backend**, kein
  `react-zeiterfassung`, keine neuen Endpunkte, keine Änderung an DTOs.
- Nur die unter `Files` gelisteten Dateien anfassen. Fällt etwas auf, das in
  einer fremden Datei liegt (auch ein echter Fehler): **melden im Kontext-Log,
  nicht still mitreparieren.**
- Kein neues Seitenlayout, keine neue Navigation. Es geht um Robustheit bei
  1440 px, nicht um Umgestaltung. Auf 1920×1080 soll alles aussehen wie heute —
  einzige gewollte Ausnahmen: die umbenannten Projekt-Reiter und die
  vollständigen Menü-Beschriftungen.

**Pflichtlektüre vor dem ersten Edit** (als Dateien lesen, **nicht** über das
Skill-Tool aufrufen)

- `docs/agent instructions/docs/FRONTEND_UI.md`
- `.claude/skills/handwerkerprogramm-design/SKILL.md` und `README.md` im selben Ordner
- `.claude/skills/playwright-design-pruefung/SKILL.md`
- `.claude/skills/loese-problem/references/kriterien.md`

**Testgetrieben**

Erst der rote Test bzw. die rote Spec, dann die Umsetzung. Bei einer
Layout-Änderung heißt „rot": die Spec misst den Missstand (Überstand in px,
gekürzter Text, Knopf außerhalb der Karte) und schlägt auf dem heutigen Stand
fehl. Wer die Spec erst nach dem Fix schreibt, hat nichts bewiesen.

**Playwright-Pflicht**

Jeder Task, der `.tsx`/`.ts` unter `react-pc-frontend/src/` ändert, liefert
eine Spec unter `react-pc-frontend/e2e/` für genau seinen Ablauf:

- `/api` vollständig gestubbt (Vorbild: `e2e/bearbeiten-leiste.spec.ts`,
  Funktion `stubbeLieferantApi`). Kein Backend, keine echten Personendaten.
- Dummy-Daten mit den **langen Namen aus der Spec**:
  Kunde `Wohnungsbaugesellschaft Beispielstadt Nord mbH und Co. Verwaltungs KG`,
  Lieferant `Stahlhandel Beispiel GmbH und Co. KG`,
  Bauvorhaben `Treppenanlage mit Podest und Absturzsicherung Bürogebäude Beispielstraße`,
  Nutzer `Friederike Beispiel-Musterfrau`.
- Je Zustand ein `designPruefung(page, testInfo, '<name>', { primaerAktion })`.
  Die Spec läuft automatisch in beiden Größen (`pc-14zoll` 1440×900,
  `pc-monitor` 1920×1080). Grün in nur einer Größe ist rot.
- Keine pixelgenauen Screenshot-Vergleiche (`toHaveScreenshot`).

**Grüne Gates je Task — nie die ganze Suite**

Aus `react-pc-frontend/`, mit dem im Task genannten eigenen Port:

```
E2E_PORT=<port> npx playwright test e2e/<eigene-spec>.spec.ts
npx vitest run <eigene Testdateien>
npm run lint
npm run build
```

`npm run test` (alles) und `npm run test:e2e` (alles) gehören den
Review-Agenten, nicht den Coding-Agenten. `lint` ist das am häufigsten
gerissene Gate — nicht überspringen.

**Build-Artefakte**

`npm run build` schreibt nach `src/main/resources/static/` (siehe
`react-pc-frontend/vite.config.ts` Z. 10). Das ist Build-Output und gehört
**nicht** ins Repo. Vor dem Commit verwerfen:

```
git checkout -- src/main/resources/static
```

bzw. schlicht nicht stagen. `git status` vor dem Commit prüfen.

**Commits**

Deutsch, Conventional-Commit-Präfix (`fix:`, `refactor:`, `test:`, `chore:`).
**Keine** `Co-Authored-By`-Zeile, keine Erwähnung von Claude/KI in Message,
Body oder Author-Feld — feste Vorgabe des Nutzers.

**Sprache und Design**

Deutsch, Handwerker-Sprache, kein Buchhalter-Deutsch. Farben nur rose/slate
aus dem Design-System (kein blue/indigo/violet), Icons nur Lucide, kein Emoji,
`rounded-lg` als Standard, `shadow-sm` für Karten. Bestehende Abweichungen
(die farbigen Kennzahl-Kästen in Kunde und Lieferant) bleiben, wie sie sind —
Farbänderungen sind nicht Teil dieses Vorhabens.

**Kürzung mit „…"**

Eine Kürzung ist nur dort erlaubt, wo sie ausdrücklich gewollt ist, und dann
trägt das Element das Attribut `data-kuerzung-erlaubt` (siehe Spec E.3). Heute
sind das genau zwei Fälle: der Anzeigename in der Menüleiste (voller Name
steht im Menü darunter) und Kartentitel mit `line-clamp-2` (voller Name steht
im `title`). Jede weitere Kürzung, die eine Spec findet, ist ein Fehler —
umbrechen lassen, nicht markieren. Wer doch markiert, schreibt die Begründung
als Kommentar daneben und ins Kontext-Log.

**Wenn eine Prüfung an einer fremden Datei anschlägt**

Nicht abschalten, nicht überspringen. Befund ins Kontext-Log, Spec so
schneiden, dass sie den eigenen Ablauf prüft, und weiter.

## Korrekturen an der Spec (am Code vom 05.09.2026 geprüft)

- **Kundeneditor hat kein eigenes Raster.** `Kundeneditor.tsx` Z. 482 nutzt
  dieselbe `DetailLayout`-Komponente wie Projekt, Anfrage, Lieferant und
  Mitarbeiter. Die in der Spec genannten 1002/334 px sind genau das 3fr/1fr aus
  `DetailLayout.tsx` Z. 17. Task 2 erledigt das mit; in `Kundeneditor.tsx` ist
  dafür **nichts** zu tun. Das eigene Raster dort (Z. 275,
  `grid grid-cols-2 gap-4 flex-1 max-w-md`) ist die Kennzahlen-Reihe der
  Kopfzeile — die gehört zu Task 5.
- **Der Reiter-Umbau bricht keinen bestehenden Unit-Test.** Die Reiter-Texte
  „Ein-/ Ausgangsgeschäftsdokumente", „Materialkosten (n)" und „Bau Tagebuch"
  kommen in keiner `*.test.tsx` vor (geprüft mit Grep über `src/`). Trotzdem
  gehört die Prüfung in Task 3: wenn beim Umbenennen doch ein Test rot wird,
  wird er **im selben Task** mit umbenannt.
- **Löschen-Knopf im Projekt-Kopf gibt es nicht.** `ProjektEditor.tsx` Z. 1099
  hat nur „Bearbeiten" und „mit Anfrage zusammenführen". Der Löschen-Knopf
  steht im Anfrage-Kopf (`AnfrageEditor.tsx` Z. 1007 ff.).
- **`.line-clamp-2` ist projekteigenes CSS** (`src/index.css` Z. 27) mit
  `-webkit-box` + `overflow: hidden`, **ohne** `text-overflow: ellipsis`. Die
  Kürzungsprüfung aus Spec E.3 muss deshalb beides erfassen: `text-overflow:
  ellipsis` (das ist `truncate`) **und** ein gesetztes `-webkit-line-clamp`,
  dessen Inhalt tatsächlich höher ist als der Kasten. Sonst greift die Prüfung
  bei genau den Elementen nicht, für die die Ausnahme `data-kuerzung-erlaubt`
  überhaupt erfunden wurde.
